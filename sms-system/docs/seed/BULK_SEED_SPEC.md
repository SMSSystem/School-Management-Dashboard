## 1. Purpose and Goals

This is a **one-off local tooling exercise**, not a product feature — it does not ship to end users and has no UI of its own. It exists to create one dedicated "stress-test" institution, populated with enough realistic dummy data to serve two purposes at once:

1. **Stress-test this app's current implementation** — exercise every list page, every generation function (Report Cards, Progress Reports, attendance summaries), every role's dashboard, and every read/write path under a data volume an order of magnitude larger than anything this codebase's existing scripts or tests have been run against.
2. **Simulate what a real academic institution's first term would actually look like** inside this app, end to end — so gaps in UX, missing empty-states, pagination behavior, and query performance at scale can be observed before a real institution ever integrates.

The institution, its users, and all of its data are considered fully disposable — see [§12](#12-teardown--cleanup-plan).

## 2. Non-Goals

- **Not a permanent seeding/demo-data tool.** `docs/guides/DEMO_TESTING_GUIDE.md` already covers the small, manual, sales-demo walkthrough use case — this spec does not replace or extend that guide.
- **Not a load-testing tool for concurrent traffic.** This seeds data sequentially, at a deliberately throttled pace, specifically to _avoid_ generating traffic spikes — it says nothing about how the app behaves under many simultaneous live users hitting it at once.
- **Not a permanent addition to `scripts/`'s migration tooling.** The existing scripts (`migrate-to-institutions.mjs`, `backfill-department-ids.mjs`, `backfill-registration-directory.mjs`) are one-time data-shape migrations for the real, shared institutions. This seed script is deliberately isolated to one throwaway institution and must never touch any other institution's data (see [§13](#13-risks-and-accepted-tradeoffs)).
- **Does not populate Events, Announcements, or Lessons.** These three collections have full Firestore rules and TypeScript types, but their create/edit forms (`EventForm`, `AnnouncementForm`, `LessonForm`) are stub components that only `console.log()` their input — they have never actually written to Firestore. Seeding data the real UI cannot itself create or edit would misrepresent what's "currently functional." If these features are wired up in the future, this spec should be revisited.
- **Does not attempt to measure or predict remaining daily quota.** Firestore/Firebase Auth expose no "quota remaining today" API on the Spark plan — see [§11](#11-error-handling-and-quota-exhaustion-fallback).

### 4.3 Daily pacing

At the decided **~10,000 writes/day** budget:

```text
~102,000 total writes ÷ 10,000/day ≈ 10–11 daily runs to completion
```

(revised from the original ~90,000 ÷ 10,000 ≈ 9–10 runs — see [§4.1](#41-estimated-total-volume-single-term-2500-users-full-realism))

This leaves **~10,000 writes/day (50%) and ~50,000 reads/day (100%, essentially untouched)** free for real institutions and developer activity on `school-sms-v1` throughout the seeding window.

### 4.4 Storage

Even at ~95,000 documents, estimated total storage is well under 100 MB (small documents; the largest per-doc payloads are the map-embedded attendance rosters at a few KB each) — **nowhere near** the 1 GiB Spark storage cap. Storage is not a constraint for this exercise.

## 5. Data Generation Strategy

- **`@faker-js/faker`** is added as a new **devDependency** (not shipped in the production bundle — same category as `firebase-admin`/`firebase-tools`, already dev-only tooling). Used for names, addresses, phone numbers, and other realistic-looking filler content.
- **Emails** use a clearly fake, non-deliverable domain scoped to this seed — `<slugified-institution-name>.seed.test` (implemented in Phase 0/2a), e.g. `first.last.0042@jones-and-sons.seed.test` — so there is no risk of the script ever emailing a real person or colliding with a real account.
- **Determinism**: the script seeds Faker's RNG with a fixed value at the start of each run, so re-running against the same checkpoint state (e.g. after a crash) regenerates the _same_ names for the _same_ logical user index — avoiding accidental duplicate-but-differently-named records if a phase partially reruns.
- Institution name, address, and branding fields are also Faker-generated but clearly labeled as a test institution (e.g. name suffixed `(Seed Test Institution)`), so it's unmistakable in any admin-facing list (this matters for [§13](#13-risks-and-accepted-tradeoffs) — this institution must never be mistaken for a real one by anyone with `super_admin` access).

## 6. Auth Account Creation

- Uses the Firebase Admin SDK (`firebase-admin/auth`), run locally with a service-account key — the same credential pattern as the existing `scripts/*.mjs` migration scripts (gitignored key, never committed, "run locally only" per their own docstrings).
- **`auth().createUser()`, called per-account in modest concurrent batches (e.g. ~20-50 in flight at once), is the primary approach** — not `importUsers()`. `importUsers()` is built for _migrating already-hashed_ passwords from another system: importing _with_ a password requires exactly matching the project's configured hash algorithm/rounds/salt (typically SCRYPT with project-specific parameters). Get that config wrong and accounts are silently unable to sign in — Firebase only re-hashes on a _successful_ sign-in, so a bad import produces no error at write time, just accounts that mysteriously can't log in, discovered later. `createUser()` sidesteps this entirely: it accepts a plaintext password directly and Firebase hashes it correctly server-side, guaranteed to work. It's slower per-account than a 1,000-per-call bulk import, but there's no bulk endpoint built for "mint brand-new plaintext passwords" anyway, so `importUsers()`'s throughput advantage doesn't actually apply to this use case. (`importUsers()` remains available as a fallback only if `createUser()`'s per-account round-trips prove too slow in practice — not expected at 2,500 accounts.)
- **Auth account creation is on a separate quota from Firestore** — standard-provider sign-ups aren't subject to the 20,000 writes/day Firestore cap at all. This means all 2,500 Auth accounts can realistically be created in a single run, decoupled from the multi-day Firestore write pacing in [§4.3](#43-daily-pacing) — only the _matching_ `users/{uid}` Firestore documents (Phase 2's other half, see [§7](#7-collection-generation-plan-write-order)) need to respect the ~10,000/day budget.
- **One shared, clearly-labeled test password** is used for all 2,500 accounts (decided in [§3](#3-scope-parameters-finalized)) — documented in the script's own header comment and in this spec, not treated as a secret (this is an isolated, disposable institution nobody else has any reason to sign into).
- Every seeded `users/{uid}` Firestore document is written via the Admin SDK too (bypasses `firestore.rules` entirely, same as the Admin SDK's Firestore writes elsewhere in this script — this is expected and accepted for a local, trusted, service-account-authenticated script; see [§13](#13-risks-and-accepted-tradeoffs)).

### 7.1 Phase 0/1 gate requirements (verified against actual gate logic, not assumed)

Neither of the app's two "setup wizards" needs to actually run — the script just has to write documents shaped the way each wizard's _completion_ leaves them:

- **Report Card generation's `profileComplete` gate** (`generateReportCard.ts:50`) is a literal stored boolean, read directly off the institution document with no other computed condition: `if (!inst.profileComplete) return { ok: false, error: ... }`. Phase 0 must write `institutions/{id}` with exactly the field set the real wizard writes on completion (`institution-profile/index.tsx:270-291`), not just the bare flag:

  ```text
  name, motto, phone, email, address, logoUrl,
  authorizedSignature: { mode: 'text' | 'image', text | imageUrl },
  classSupervisorLabel   (defaults to "Class Supervisor" if blank)
  gradeSupervisorLabel   (defaults to "Grade Supervisor" if blank)
  principalLabel         (defaults to "Principal" if blank)
  vicePrincipalLabel     (defaults to "Vice Principal" if blank)
  gradingSystem: 'flat' | 'weighted'
  profileComplete: true
  ```

- **The academic calendar has no equivalent stored flag.** Whether it's "set up" is derived purely from data shape, computed live on every read (`src/hooks/useInstitutionAcademicCalendar.ts`): an `academicYears` document with `status: 'active'`, and a `terms` document whose `startDate`/`endDate` bracket _today's real calendar date_. Phase 1 must pick term dates that cover today at write time — and keep covering it for the full ~10 day seeding window (see [§4.3](#43-daily-pacing)), since this is recomputed against the real clock on every read, not stored once.

### 7.2 Phase 3-7 corrections and finalized design (verified against actual form components)

Building Phases 3-7 meant reading `HouseForm.tsx`, `DepartmentForm.tsx`, `ClassForm.tsx`, `SubjectForm.tsx`, `TimetableSlotForm.tsx`, `ExamForm.tsx`, `AssignmentForm.tsx`, and the Gradebook page/`ColumnCreationModal.tsx` directly, rather than assuming their write shapes. That surfaced four real corrections to this spec's original Phase 4/5 assumptions, plus a finalized subject/class design that changes the volume estimates in [§4](#4-free-tier-cost-analysis-and-daily-pacing):

- **`subjectEnrollments` was missing from [§7](#7-collection-generation-plan-write-order) entirely.** `SubjectForm.tsx`'s real create path always writes one `subjectEnrollments/{subjectId}_{classId}` doc per class a subject applies to — the Subject/My/Child Attendance pages ([§8](#8-page-by-page-ui-coverage-checklist)) read from it. Without it, those pages would show nothing for the seeded institution despite everything else being populated. Now part of Phase 4 (378 docs — one per subject-class pairing).
- **`ClassForm.tsx`'s `supervisor` field is free text, not a teacher UID reference.** `ClassDocument`'s `classTeacherId` field (whose comment claims it's "required by `isClassTeacherFor()` rule") is in fact never written anywhere in the app — a pre-existing, unrelated dead field, not something this seed needs to populate. Phase 4 sets `supervisor` to a real senior teacher's display name (a string), matching what the real form actually produces.
- **`SubjectForm.tsx`'s teacher picker only ever lists `regular_teacher`**, never `senior_teacher` (verified by reading its Firestore query). Phase 4's `subjects.teacherIds` are drawn from the 92-person `regular_teacher` pool only, round-robin (~7-8 teachers/subject).
- **Phase 5's `updateDoc` calls are not free.** The original Phase table listed Phase 5 as "0 (updates only)" — but a Firestore `update` consumes a write op against the daily quota exactly like a `set`/`create`. Corrected to ~1,250 (1 update/student).
- **Finalized subject/class design** (Phase 4): 12 subjects — 8 "core" subjects apply institution-wide (every one of the 42 classes); 4 "elective" subjects are class-scoped, each class assigned exactly one of the 4 round-robin. Every student ends up with 8 core + 1 elective = **9 subjects**, not the ~8 this spec originally assumed for [§4](#4-free-tier-cost-analysis-and-daily-pacing)'s `results`/`feedback_comments` estimates (both revised there accordingly). 42 classes = 6 grades (7-12) × 7 sections (A-G).
- **`student_parents` uses deterministic sibling-family clustering, not a flat 1:1 parent:student mapping.** Students are grouped into families of 1-4 (weighted toward smaller), and each family gets 2 parents (mother+father) while the 1,117-parent pool lasts, 1 for the family that gets the last odd one out, or 0 once the pool is exhausted — meaning roughly the last ~10-15% of students end up with no parent link (realistic — incomplete guardian records happen at real institutions — not a scripting shortcut). Because most links are "2 parents × N siblings" rather than 1:1, the actual link count (measured: 1,907) runs meaningfully higher than a naive parent-count-based estimate.
- **All Phase 4 reference data uses deterministic IDs** (`house_<slug>`, `dept_<slug>`, `class_g<grade><section>`, `subject_<slug>`, and gradebooks' existing `<classId>_<subjectId>_<termId>` scheme) — consistent with [§9](#9-script-architecture)'s idempotency strategy, and unlike the `addDoc`-random-ID pattern the live UI forms use (which is fine for a human clicking "Create" once, but would make a resumed script run non-idempotent).

The net effect on [§4](#4-free-tier-cost-analysis-and-daily-pacing)'s totals: Phases 3-7 measured ~6,963 writes combined, versus this spec's original combined estimate of ~2,200-2,800 for those same phases — roughly 4,000-5,000 more than expected, plus a further ~7,000 from the 8→9 subjects/student revision to the still-unbuilt Phase 8/9. Total revised estimate: **~96,000-100,000** (was ~87,000-95,000), **~10 daily runs** (was ~9-10) — a modest, one-run shift, not a re-scoping.

### 7.3 Phase 10-12 corrections and finalized design

Building Phases 10-12 meant reading `attendance/general/index.tsx`, `attendance/subject/index.tsx`, `attendanceSummaryUtils.ts`'s `rebuildSummariesForClass()`, and `attendanceCalendar.ts` directly, the same approach [§7.2](#72-phase-3-7-corrections-and-finalized-design-verified-against-actual-form-components) took for Phases 3-7. That surfaced one real correction to this spec's original volume assumption, plus a few design decisions worth recording:

- **Attendance dates span the full _stored_ term range (`cp.termStartDate`..`cp.termEndDate`), not a "typical" ~63-school-day term.** [§4.1](#41-estimated-total-volume-single-term-2500-users-full-realism)'s original `generalAttendance`/`subjectAttendance` estimates assumed a term of ~63 school days (⅓ of a ~190-day academic year). But Phase 1 ([§7.1](#71-phase-01-gate-requirements-verified-against-actual-gate-logic-not-assumed)) deliberately widened the _stored_ `terms` document's date range to ~120 days past "today" — purely so the academic-calendar gate (`useInstitutionAcademicCalendar`) stays satisfied across this script's own multi-day seeding window, not because a real term is that long. Phase 12's `attendanceSummaries` computation reads that exact same stored range for its `totalExpectedSessions` denominator (`countExpectedSessions(termStartDate, termEndDate, ...)`, mirrored from `attendanceCalendar.ts`), so generating attendance for only a ~63-day subset of it would make every seeded student's `attendanceRate` look artificially low — a stress-test artifact (a report card or progress report showing every student at ~65% attendance), not a realistic "partial term" state. Phases 10 and 11 therefore both generate across the same full stored range Phase 12 measures against. Since this is disposable, fully-synthetic dummy data (not a real register anyone is filling in day-by-day), backdating/forward-dating records relative to the real calendar date carries no realism cost. This raised `generalAttendance` from [§4.1](#41-estimated-total-volume-single-term-2500-users-full-realism)'s original ~5,300 estimate to a measured ~8,148 (~97 school days instead of ~63); `subjectAttendance` landed at a measured ~8,967, within the original ~8,000-10,000 range (whose session-frequency assumption was explicitly left unfinalized until this phase was built).
- **Both collections use deterministic doc IDs** (`ga_<classId>_<date>_<session>`, `sa_<subjectId>_<classId>_<sessionDate>`), unlike the live UI's `addDoc`-random-ID pattern — consistent with [§9](#9-script-architecture)'s idempotency strategy and the same choice already made for Phase 4/7's reference data.
- **Attendance states are drawn from a realistic weighted distribution** (mostly Present, a mix of Absent/Late/Sick/Excused) that deliberately excludes `B` ("Blank" per `attendanceStates.ts`) — that state exists for a teacher to manually exclude one session from one student's own expected-session count, a deliberate per-record override rather than something a bulk-realism generator should invent on its own.
- **`subjectAttendance` has no canonical exported TypeScript type** (unlike every other seeded collection, which has a `...Document` type in `src/lib/firebase.ts`) — its write shape is only defined as a local interface inside `attendance/subject/index.tsx`. Phase 11's payload was verified against that component's `commitSave()` directly rather than against a type declaration.
- **Phase 12 is a generation-equivalent reimplementation, not a literal "click Rebuild" automation.** `rebuildSummariesForClass()` is a client-SDK helper (imports from `firebase/firestore`) that cannot run inside this Admin-SDK `.mjs` script, so Phase 12 reimplements its exact math (same per-student `P`/`A`/`L`/`S`/`E`/`B` tally, same `totalExpectedSessions`/`filledSessions`/`sessionsAbsent`/`attendanceRate` formulas, same `${studentId}_${termId}` doc ID) against the Admin SDK. It reads Phase 10's `generalAttendance` docs back from Firestore (rather than reusing Phase 10's in-memory item list), so it stays correct even when run in a separate invocation, potentially days after Phase 10 finished writing — consistent with every other phase's checkpoint-driven, re-derive-don't-persist approach.
- **No `nonSchoolDays` documents are seeded** — that collection isn't in [§7](#7-collection-generation-plan-write-order)'s write list for this seed, so every weekday in the attendance date range counts as a school day for both generation (Phase 10/11) and the expected-session math (Phase 12).

### 7.4 Phase 13-17 corrections and finalized design

Building Phases 13-17 meant reading `list/students/[id]/index.tsx` (activity/responsibility writes), `DisciplinaryActionForm.tsx`, `report-card-comments/index.tsx`, `src/lib/generateReportCard.ts`, `report-cards/index.tsx`'s `handleBatchGenerate()`, `src/lib/generateProgressReport.ts`, `register/[institutionId]/index.tsx`, and `RegistrationDirectoryToggle.tsx` directly, the same approach [§7.2](#72-phase-3-7-corrections-and-finalized-design-verified-against-actual-form-components)/[§7.3](#73-phase-10-12-corrections-and-finalized-design) took for earlier phases. This was the largest and most logic-heavy phase group to date — `generateReportCard.ts` alone runs an 18-step pipeline — and surfaced several real corrections:

- **Phase 15 splits into 15a/15b, doubling `reportCards`'s write-op cost against a fixed document count.** `report-cards/index.tsx`'s own `handleBatchGenerate()` is itself a two-pass flow: Pass 1 generates every card in a class with `classAverage`/`classRank` left `null` (`skipClassRankComputation: true`), because rank depends on the full cohort and computing it per-student during sequential writes would rank early students against an incomplete set; Pass 2 then reads every card back and writes `classAverage`/`classRank` in a single grouped update. This script's single-phase-at-a-time checkpoint model can't express "don't start step 2 until every class's step 1 is done" as one phase, so it's split into `15a` (generate) and `15b` (rank pass) — the same sub-phase convention `2a`/`2b` already established for Auth-then-Firestore. Net effect: 1,250 create ops + 1,250 update ops = **~2,500 write operations for only 1,250 documents**, not the ~1,250 this spec originally assumed (see [§4.1](#41-estimated-total-volume-single-term-2500-users-full-realism)'s revised total). Phase 15b's rank computation runs as one in-memory pass across the read-back cohort, rather than the two-Firestore-round-trip Pass 1/Pass 2 the real UI does (client-side, one class at a time, triggered by a button click) — same math, cheaper mechanism, since this script already has every card in hand from a single query.
- **`subjectPosition` is always `null`, despite `generateReportCard.ts`'s own per-student comment suggesting otherwise.** That comment claims it's "only computed accurately in batch flow where all classmates' results are processed together" — but reading `handleBatchGenerate()` shows it never actually touches `subjectPosition` in either pass. This is a pre-existing gap in the real feature, not something this seed should paper over by inventing a computation the live UI itself doesn't perform — Phase 15a leaves it `null` for every subject row, faithfully matching current behavior.
- **Every seeded result is `source: 'gradebook'`** (Phase 8's own payload), so `generateReportCard.ts`'s non-gradebook coursework/exam-weight branch is dead code for this seed's data — Phase 15a only reimplements the gradebook branch. Similarly, since every gradebook's 5 columns always sum to exactly 100% weight by construction (Phase 7's fixed `GRADEBOOK_COLUMN_SPECS`), Phase 15a skips the real function's column-weight-sum validation query entirely and reads each result's own already-embedded `columnWeight` field instead.
- **Phase 15a reuses one bulk `feedback_comments` query's results instead of the real gradebook branch's redundant per-subject `getDoc`.** `generateReportCard.ts`'s gradebook branch does its own individual `feedback_comments/{studentId}_{sid}_{termId}` read per subject even though an equivalent bulk query (`feedbackBySubject`) was already fetched moments earlier for the non-gradebook branch — the same document, same deterministic ID scheme Phase 9 already uses. Phase 15a fetches once per student and reuses it, saving up to 9 reads/student (~11,000 reads total) with byte-identical results.
- **`classPopulation`, `classId`/`houseId`/`houseName`, and subject metadata are computed from this script's own deterministic assignment functions, not re-fetched from Firestore.** `generateReportCard.ts` queries `users` for classmates-count and re-reads each student's own document for `classId`/`houseId`; this script already knows the exact deterministic membership from `classIdForStudentIndex()`/`houseNameForStudentIndex()` (Phase 5) and `buildSubjects()` (Phase 4) — reusing those pure functions instead saves roughly 1,250 + several thousand more reads without changing the result, consistent with [§9](#9-script-architecture)'s "recompute pure functions, don't re-fetch" pattern already used throughout this script.
- **`registration_directory/{id}`'s `activeAcademicYearId`/`activeAcademicYearName` were missing from Phase 0's original write.** The real public registration form (`register/[institutionId]/index.tsx`) reads these fields directly off the directory entry, not off `academicYears` — they're normally set by `RegistrationDirectoryToggle.tsx` when an institution_admin turns registrations on. Phase 17 now backfills them via a merge-update before writing its illustrative sample. **`acceptingRegistrations` is deliberately left at Phase 0's original `false`** — setting it `true` would put this disposable seed institution on the real public `/register` page for any internet visitor to submit a registration to, which is out of scope for a local stress-test exercise.
- **Illustrative registrations never use `status: 'converted'`.** That status implies a real `convertedStudentUid` pointing at an actual account — something [§13](#13-risks-and-accepted-tradeoffs) already establishes this sample deliberately never does. Phase 17 varies only `pending`/`reviewed`/`rejected`.
- **`possibleDuplicate` is always written `false`**, matching the real public form exactly — the actual duplicate flag is computed and backfilled client-side the first time an admin opens the Registrations page against real student data (`computePossibleDuplicates()` in `registrations/index.tsx`), not at submission time, so there's nothing for this script to reimplement here.
- **Progress Report's 5-per-student-term retention cap (`enforceProgressReportCap()`) is not reimplemented.** This seed only ever generates exactly 1 progress report per student per term, well under the cap — the cap-enforcement query/delete logic is simply never exercised at that volume, so replicating it would be dead code.
- **All of Phase 13/14/15a/16/17's writes use script-chosen deterministic IDs** (`act_<uid>_<n>`, `resp_<uid>_<n>`, `disc_<uid>_<n>`, `rcc_<uid>_<termId>`, `rc_<uid>_<termId>`, `pr_<uid>_<termId>`, `enroll_<n>`), unlike the live UI's `addDoc`-random-ID pattern for every one of these collections — consistent with [§9](#9-script-architecture)'s idempotency strategy and the same choice already made for Phase 4/7/10/11's data.

## 9. Script Architecture

- **Language/runtime**: Node.js `.mjs` (ESM), matching the existing `scripts/*.mjs` convention exactly.
- **Credentials**: a local service-account key file (gitignored, same pattern as `scripts/service-account.json` already excluded via `.gitignore`'s `scripts/*service-account*.json` rule).
- **Checkpoint file**: a single local JSON file (e.g. `scripts/.seed-checkpoint.json`, gitignored) recording, per phase: `status` (`pending` / `in_progress` / `complete`), and enough cursor state (e.g. last-written index within a phase's generation loop) to resume mid-phase, not just at phase boundaries — a phase like Phase 8 (`results`, ~56,000 writes) cannot be all-or-nothing against a 10,000-write daily budget; it must be resumable _within itself_ across multiple days.
- **Idempotency**: every write within a phase uses a deterministic, derivable document ID or a pre-computed existence check, so re-running a partially-completed phase (whether resuming normally or recovering from an unexpected interruption) never creates duplicate documents. Where the app's own conventions already use deterministic IDs (`attendanceSummaries`, `feedback_comments`, `student_parents`), the script reuses those same ID schemes; where the app uses `addDoc`-style random IDs (`results` — the sole remaining exception, see [§13](#13-risks-and-accepted-tradeoffs)) the script's per-batch checkpoint cursor (`onProgress`, see [§7.3](#73-phase-10-12-corrections-and-finalized-design)) tracks exactly how many have been written instead. Every other collection this script writes to — including several (`houses`/`departments`/`classes`/`subjects`/`subjectEnrollments`, `gradebooks`/columns, `generalAttendance`/`subjectAttendance`, `studentActivities`/`studentResponsibilities`/`disciplinaryActions`, `reportCardComments`, `reportCards`, `progressReports`, `enrollmentRegistrations`) whose live UI forms use `addDoc` — instead uses a script-chosen deterministic ID (slugs / `<classId>_<subjectId>_<termId>` / `<uid>_<termId>` / etc.), a deliberate departure from the live UI's own random-ID convention made specifically for this script's resumability needs — see [§7.2](#72-phase-3-7-corrections-and-finalized-design-verified-against-actual-form-components)/[§7.4](#74-phase-13-17-corrections-and-finalized-design).
- **Per-run write budget**: the script tracks a running write counter for the current invocation and stops cleanly (persisting the checkpoint) once it reaches the ~10,000/day budget, even if the current phase isn't finished — it does not attempt to finish "just one more phase" past budget.
- **Batching**: reuses the existing `BATCH_LIMIT = 450` convention from `scripts/migrate-to-institutions.mjs` / `backfill-department-ids.mjs` / `src/lib/spreadsheetImport.ts` (safety margin under Firestore's hard 500-operation batch cap).
- **Logging**: each run prints a summary (phase, writes this run, cumulative writes, estimated runs remaining) to stdout, and Windows Task Scheduler is configured to redirect that output to a local log file for later review without needing to watch the console live.

## 10. Daily Trigger — Windows Task Scheduler

Implemented as two PowerShell scripts (§15):

- **`scripts/run-seed-bulk-institution.ps1`** — the wrapper Task Scheduler actually invokes. Task Scheduler's execution environment is minimal and can't be relied on to carry the interactive shell's `PATH` or working directory, so this wrapper resolves `node.exe` and the service-account key path explicitly, sets the working directory to `sms-system/`, and redirects all output to a timestamped log file under `scripts/logs/` (gitignored — already covered by the repo's existing top-level `logs`/`*.log` rules, no new `.gitignore` entry needed) — the "redirect that output to a local log file for later review" behavior [§9](#9-script-architecture) already called for.
- **`scripts/register-seed-task.ps1`** — a separate, one-time setup script that actually registers the Windows Scheduled Task (via `Register-ScheduledTask`) to run the wrapper daily. _Not run as part of building this script, and not run by anyone until after [§14](#14-implementation-order) item 10's PR is reviewed and merged to `main`_ — registering it against a local feature-branch checkout now would point the live, unattended, once-a-day-for-over-a-week automation at code nobody has reviewed yet, defeating exactly the safeguard item 10 exists for. This script is meant to be run manually, later, from the merged `main` checkout.

Finalized configuration decisions (previously left open, now settled):

- **Trigger time**: once daily at 03:00 local time by default (a low-traffic hour on a personal dev machine), overridable via `register-seed-task.ps1 -TriggerTime`.
- **Logon requirement**: `LogonType Interactive` — the task only fires while the configured Windows user is logged on. Deliberately not "run whether logged on or not," which would require either storing this Windows account's password in Task Scheduler or running as `SYSTEM` (risking a different/missing `PATH` for `node.exe`) — disproportionate for a tool this spec already frames as a personal-dev-machine convenience, not a server automation.
- **Retry-on-failure policy**: none (no `-RestartCount`/`-RestartInterval`). [§11](#11-error-handling-and-quota-exhaustion-fallback) already establishes that the seed script itself stops cleanly on any error and relies on the *next scheduled run* to resume from the checkpoint — an OS-level retry loop on top of that would reintroduce the exact "backoff-and-hammer" behavior §11 explicitly rejects, just one layer up.
- **Wake-the-machine**: disabled. A personal dev machine should not be woken from sleep by a background stress-test tool.
- **Network/battery**: requires network availability to start; allowed to run and continue on battery power, in case the development machine is a laptop.
- **Resilience** (unchanged from the original design): because the checkpoint file is the sole source of truth for progress, a missed day (machine off, asleep, logged out, or the task simply not firing) costs nothing but time — the next successful run resumes exactly where the last one left off. No day-counting or date-based logic is needed in the script itself; it always just "does today's budget of work, starting from the checkpoint."

## 11. Error Handling and Quota-Exhaustion Fallback

Firestore/Firebase Auth expose no client-queryable "quota remaining today" endpoint on Spark — the daily cap is only detectable reactively, via a write actually failing with a `resource-exhausted` (or equivalent quota) error. Per the finalized decision:

- On any such error, the script **stops immediately** — no retry loop, no backoff-and-hammer behavior that could make the situation worse for real traffic sharing the same project.
- The checkpoint is persisted **up to the last successful write** before the failure (never past it), so the next scheduled run resumes cleanly.
- This can happen even under the script's own conservative ~10,000/day self-imposed budget if real traffic on `school-sms-v1` consumes an unexpectedly large share of the shared 20,000/day cap on a given day — this is an accepted, self-healing scenario, not a failure condition requiring intervention.
- Any other (non-quota) error — a malformed record, an unexpected missing reference — is logged with full context (phase, record index, error) and also stops the run rather than silently skipping, so data-integrity problems can't accumulate unnoticed across a multi-day run.

## 12. Teardown / Cleanup Plan

Since this is explicitly throwaway stress-test data, cleanup needs its own plan — Firestore has no cascade-delete, so every nested collection must be deleted explicitly, and Auth accounts are a separate deletion entirely from their Firestore documents.

- A companion script (e.g. `scripts/teardown-bulk-institution.mjs`) reads the same institution ID the seed script used, and:
  1. Deletes every document in every `institutions/{id}/{collection}` subcollection (iterating each collection named in [§7](#7-collection-generation-plan-write-order), batched at the same 450-op limit).
  2. Deletes the `users/{uid}` documents and `student_parents/{id}` links for all 2,500 seeded people (identified via the checkpoint file's recorded UID list, not a broad query, to guarantee zero risk of touching any real institution's data).
  3. Deletes the corresponding 2,500 Firebase Auth accounts via `auth().deleteUsers()` (bulk delete, up to 1,000 UIDs per call — 3 calls) — the efficient counterpart to `importUsers()` used for creation.
  4. Deletes the `institutions/{id}` and `registration_directory/{id}` documents last.
- Like the seed script itself, teardown respects the same daily write/delete budget and is resumable via its own checkpoint — deleting ~100,000 documents (see [§4.1](#41-estimated-total-volume-single-term-2500-users-full-realism)) is itself a multi-day operation under the same Spark constraints (Firestore deletes share the 20,000/day delete quota, separate from but just as real as the write quota).
- Teardown is **not run automatically** after seeding completes — it's a separate, deliberately-invoked script, run whenever the stress test is actually finished with.

### 12.1 Implementation notes (§14 item 9)

`scripts/teardown-bulk-institution.mjs` is a companion, not a wrapper — it never imports or calls the seed script. It reads `scripts/.seed-checkpoint.json` as read-only source data (the pinned `institutionId`, the full roster with each person's Auth `uid`, and Phase 3's `familyLinks`) and never modifies it. A few design points worth recording, verified against the seed script's own checkpoint shape while building this:

- **Its own checkpoint, pinned once.** `scripts/.teardown-checkpoint.json` (gitignored, same as the seed checkpoint) tracks teardown's own per-phase progress across multiple daily runs. On first run it copies `institutionId` out of the seed checkpoint once and pins it — mirroring the seed script's own Phase 0 pinning pattern — so a teardown resumed days later keeps targeting the same institution even if the seed checkpoint file is later edited or replaced.
- **`users`/`student_parents` are deleted by explicit ID list, never by query**, matching §12/§13's "own internal correctness is the only safety net" requirement exactly: `users/{uid}` refs come straight from the seed checkpoint's roster; `student_parents/{parentUid}_{studentUid}` doc IDs are derived from the seed checkpoint's own `familyLinks` (resolved back to UIDs via that same roster), not recomputed or re-queried.
- **Every institution-nested collection (§7's list, 21 of them) shares one generic paginated-delete runner** — repeatedly query a budget-sized page and batch-delete it; a page shorter than requested proves the collection is now empty, which is what marks that phase complete. No resume cursor is needed beyond that, since a deleted document can never reappear in a later page. `gradebooks` is the one exception (its `columns` subcollection isn't cascade-deleted by deleting the parent doc), so it gets its own runner that deletes each gradebook's columns before the gradebook itself, one gradebook at a time so the per-document budget accounting stays exact.
- **A live-mode-only safety check** (`verifySeedInstitutionName`) reads `institutions/{id}`'s stored `name` before any deletion and refuses to proceed if it doesn't end with `(Seed Test Institution)` — a second gate beyond "the checkpoint says so," in case a stale or mismatched checkpoint file ever gets pointed at the wrong document (§16 Operating Rule 2's handoff risk). A missing document is treated as "an earlier teardown run already finished," not a failure.
- **Dry-run touches Firestore/Auth not at all**, matching the seed script's own dry-run contract exactly ([§11](#11-error-handling-and-quota-exhaustion-fallback)) — including skipping the safety check above and every collection's existence probe. Each nested-collection phase just prints a generic "would drain via paginated batch delete" message; only the checkpoint-known counts (roster length, link-list length) are printed for `users`/`student_parents`/`auth`.
- **Auth account deletion mirrors §6's account-creation precedent**: not paced by the Firestore delete budget (separate quota), chunked only at `deleteUsers()`'s own 1,000-UID-per-call limit, and treats a per-account `auth/user-not-found` error as expected on a resumed run (already deleted) rather than a hard failure — any other error still stops the run per [§11](#11-error-handling-and-quota-exhaustion-fallback).
- **Closed a real gap in [§15](#15-files):** that table already specified `package.json` should gain `seed:bulk`/`teardown:bulk` npm scripts, but implementation item 2 never actually added them. Both are now added (`node scripts/seed-bulk-institution.mjs` / `node scripts/teardown-bulk-institution.mjs`), alongside this item's own `scripts/teardown-bulk-institution.mjs` and `scripts/.teardown-checkpoint.json`.
- **Verified via dry-run against a synthetic seed checkpoint only** (a small fabricated roster + family-link list, the same methodology [§7.4](#74-phase-13-17-corrections-and-finalized-design) used) — the seed script has never been run live, so there is no real seeded data yet to tear down; this script's live-mode delete paths (query pagination, gradebook column deletion, Auth `deleteUsers()`) remain unexercised against a real Firestore project. This is the same disclosed limitation as every other phase built so far.

## 13. Risks and Accepted Tradeoffs

- **Shared project quota**: `school-sms-v1` is the one Firebase project behind every real institution and every dev/test session. The ~10,000/day self-imposed budget is a mitigation, not a guarantee — a real institution having an unusually heavy day at the same time could still contend for quota. This was weighed explicitly and accepted rather than paying for Blaze.
- **Admin SDK bypasses `firestore.rules` and App Check entirely.** This is expected and standard for a trusted, local, service-account-authenticated script (identical to how the existing `scripts/*.mjs` migration tools already operate) — but it means the seed script's own internal correctness (never writing to any institution ID other than its own dedicated one) is the _only_ safety net, since the rules layer that protects every other write path in this app does not apply here. The script must hard-code / checkpoint-record its one target institution ID and never derive it from anything queried at runtime.
- **`importUsers()`'s password-hash requirements** would have been awkward to satisfy for a simple shared plaintext password, so [§6](#6-auth-account-creation) settled on `createUser()` in modest concurrent batches as the primary mechanism (confirmed in the implemented Phase 2a) rather than leaving this open — `importUsers()` remains available only as a fallback if `createUser()`'s per-account round-trips prove too slow in practice.
- **Role ratio realism**: 8/33/92/1,250/1,117 is a deliberately-chosen realistic staff:student ratio (~1:11), not the literal pyramid numbers first proposed — a documented, explicit judgment call, not a default.
- **Single term only**: this seed does not exercise cross-term behavior (e.g. a student's Progress Report history spanning multiple terms, term-to-term promotion, multi-year Report Builder batches). That's an explicit scope cut, not an oversight — extending to multiple terms later is straightforward (multiply the relevant phases) but was deliberately deferred to keep this exercise's cost and runtime bounded.
- **`enrollmentRegistrations` sample data (Phase 17) is illustrative only** — those records are never actually converted into accounts (the 2,500 users all come from Phases 2a/2b's direct Admin SDK creation), so the Registrations page will show entries whose "Convert to Account" action, if clicked, would create _additional_ accounts beyond the planned 2,500. This is acceptable for read/list-page testing but worth remembering if someone starts clicking around in that page during the stress test.
- **A checkpoint bug that re-runs an already-completed phase is not equally safe everywhere.** Deterministic-ID collections — now the large majority: `feedback_comments`, `attendanceSummaries`, `student_parents`, and (as of [§7.2](#72-phase-3-7-corrections-and-finalized-design-verified-against-actual-form-components)/[§7.4](#74-phase-13-17-corrections-and-finalized-design)) `houses`/`departments`/`classes`/`subjects`/`subjectEnrollments`, `gradebooks`/columns, `generalAttendance`/`subjectAttendance`, `studentActivities`/`studentResponsibilities`/`disciplinaryActions`, `reportCardComments`, `reportCards`, and **`progressReports`** (this seed deliberately chose a deterministic `pr_<uid>_<termId>` ID for it specifically because of this risk, even though the real live feature's own `addDoc`-based generation never upserts by design) — naturally no-op on a repeat write. Only **`results`** (Phase 8, `addDoc`-random by design — matching the live gradebook's own write pattern, since results have no natural per-student+column uniqueness key worth inventing) and `enrollmentRegistrations` (Phase 17, deliberately `enroll_<n>`-indexed against the fixed sample list, so actually already safe) remain not-inherently-idempotent. `results` is protected by the same per-batch checkpoint cursor (`budgetedBatchWrite`'s `onProgress`, see [§7.3](#73-phase-10-12-corrections-and-finalized-design)'s crash-simulation-verified fix) that makes a resumed run pick up exactly where it left off rather than restart the phase from scratch — the residual risk is narrower than originally scoped here, but not zero: a checkpoint file that's rolled back or edited by hand (§16 Operating Rule 2 already warns against this) could still cause `results` to duplicate.
- **Sequential batching is a deliberate choice, not a missed optimization.** Firestore's real constraint at this volume is per-document contention, not a global ops/sec ceiling — writing many _different_ auto-ID documents in parallel is generally safe from Firestore's side. But parallelizing this script's batch commits would make the "stop cleanly on `resource-exhausted`, resume exactly where you left off" guarantee in [§11](#11-error-handling-and-quota-exhaustion-fallback) unreliable — several in-flight commits racing to finish right as the daily cap is hit makes it much harder to know exactly how many writes landed before the first failure. Do not parallelize batch commits to "speed things up."

## 14. Implementation Order

1. Add `@faker-js/faker` devDependency.
2. `scripts/seed-bulk-institution.mjs` — Phase 0-1 (institution, academic year, term).
3. Phases 2a-2b (Auth via `createUser()` + `users` — the highest-risk, least-precedented phase; validate the account-creation approach here first, before building anything that depends on it).
4. Phase 3-7 (links, reference data, timetable/exams/assignments, gradebooks/columns).
5. Phase 8-9 (`results`, `feedback_comments` — the highest-volume phases; validate checkpoint/resume behavior mid-phase here, since these are the ones most likely to span multiple daily runs on their own).
6. Phase 10-12 (attendance registers + summaries).
7. Phase 13-17 (disciplinary/activities/responsibilities, report card comments, report cards, progress reports, illustrative registrations).
8. Windows Task Scheduler configuration.
9. `scripts/teardown-bulk-institution.mjs`.
10. **Open a PR merging all of the above into `main`, and get it reviewed before Task Scheduler is ever pointed at it.** This script authenticates via a service-account key and bypasses `firestore.rules` entirely — the rules layer that protects every other write path in this app doesn't apply here, so the script's own internal correctness (never touching an institution ID other than its one dedicated target) is the only safety net. That's exactly the kind of thing that should get a second pair of eyes before running unattended, once a day, for over a week — and Task Scheduler should be executing the reviewed, merged version, not a private local script that could silently drift from what a reviewer actually approved.
11. **After the stress test is complete and teardown has been run**, open a follow-up PR removing `scripts/seed-bulk-institution.mjs`, `scripts/teardown-bulk-institution.mjs`, the `@faker-js/faker` devDependency, and the associated npm scripts/`.gitignore` entries — per [§2](#2-non-goals), this tooling is not meant to be a permanent addition to the codebase.

## 16. Operating Rules

These apply to anyone on the team for as long as this tooling and its seeded institution exist — not just whoever runs the script.

1. **Never treat `(Seed Test Institution)` as real data.** Anyone with `super_admin` cross-institution visibility should recognize the name on sight and skip it — don't file bugs against it as if it were a live customer's institution.
2. **Only one machine/session runs the seed or teardown script at a time, ever.** The checkpoint file is local-only, not distributed — if it's ever run from a second machine or checkout without realizing a checkpoint already exists, the result is double-seeding: duplicate writes, wasted shared quota, and a checkpoint that no longer reflects reality. If someone else needs to take over running it, hand off the checkpoint file explicitly first.
3. **Never manually edit data inside the seed institution through the UI while the script is still running.** It can invalidate the checkpoint's assumptions about what's already been written — e.g. deleting a document the script believes it already created.
4. **Never commit the service-account key or the checkpoint file.** Already enforced by `.gitignore` patterns, but worth restating given how much power that key carries — the Admin SDK bypasses every rule in `firestore.rules` entirely.
5. **Be aware the seed consumes real shared quota for roughly 10 days** (see [§4.3](#43-daily-pacing)). If you're doing heavy testing of your own during that window and hit unexpected `resource-exhausted` errors on `school-sms-v1`, this is probably why — coordinate rather than being surprised, and don't file it as an app bug without checking first.
6. **Run teardown promptly once the stress test is actually finished with.** ~100,000 throwaway documents lingering indefinitely isn't free — it's unnecessary storage, and it pollutes any future cross-institution browsing or query testing.
7. **Do not extend the seed script to write to any collection or institution not explicitly listed in [§7](#7-collection-generation-plan-write-order).** Since Admin SDK writes bypass `firestore.rules`, there is no safety net catching a scope mistake here the way there would be for any other code path in this app.
